## 1. The division of responsibility

```
┌──────────────────────────────────────────────────────────────┐
│  A.  ERP PALLET / JOB BARCODE                                │
│                                                              │
│  Generated by:   the customer's existing ERP                 │
│  Printed by:     the customer's existing process             │
│  Owned by:       the customer's ERP                          │
│                                                              │
│  This system:    SCANS · DECODES · VALIDATES · REFERENCES    │
│  This system:    NEVER GENERATES · NEVER REPRINTS            │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  B.  STORAGE LOCATION BARCODE                                │
│                                                              │
│  Generated by:   THIS SYSTEM                                 │
│  Printed by:     THIS SYSTEM                                 │
│  Owned by:       THIS SYSTEM                                 │
│                                                              │
│  Identity:       permanent, one per location, never reissued │
│                  by a reprint (BRD §18)                      │
└──────────────────────────────────────────────────────────────┘
```

Confusing these two is the most consequential mistake available on this project. The
architecture prevents it structurally: there is no code path that writes a pallet barcode
value, and `pallets.raw_barcode_value` is write-once at creation.

## 2. Part A — ERP pallet barcode

### 2.1 Current state of knowledge

From the BRD, the label carries: **Job Number, Pallet Number, Customer Name, Customer LPO
Number** (BRD §2). BRD §18 requires the symbology and encoded structure to be *tested and
confirmed*; §26 requires sample labels. Neither has been provided.

**Therefore no parsing rule is written.** The system ships with the `RAW_REFERENCE` profile
and operates correctly with it, per BRD §4.3 ("If it encodes only a reference number, the
solution may store that reference").

### 2.2 Profile engine

Decoding is configuration, not code. `barcode_profiles` rows carry a strategy and a JSON
config; a single `BarcodeProfileParser` interprets them.

| Strategy | For | Config shape |
|---|---|---|
| `RAW_REFERENCE` | **Default.** Store the scanned value verbatim as the pallet reference | `{}` |
| `DELIMITED` | Fields separated by a character, e.g. `JOB\|PLT\|CUST\|LPO` | `{ "delimiter": "\|", "fields": ["job_number","pallet_number","customer_name_raw","lpo_number"] }` |
| `FIXED_WIDTH` | Fixed-position substrings | `{ "fields": [{"name":"job_number","start":0,"length":10}, …] }` |
| `REGEX` | Named capture groups | `{ "pattern": "^(?<job_number>…)(?<pallet_number>…)$" }` |
| `GS1` | GS1 Application Identifiers | `{ "ai_map": { "91": "job_number", "92": "pallet_number" } }` |

Output is always a `ParsedPalletIdentity`:

```
{ job_number?, pallet_number?, customer_name_raw?, lpo_number?,
  raw_value (always), profile_code (always) }
```

`raw_value` is stored on every pallet regardless of profile. If the profile is later
corrected once real labels arrive, existing records can be re-parsed from the raw value
rather than re-scanned in the yard.

### 2.3 Onboarding a real profile (the `OI-01` procedure)

1. Customer supplies **at least 20 real production labels** covering multiple jobs,
   customers, and any edge cases (long names, missing LPO, reprinted labels).
2. Scan each with the actual target PDA (`OI-07`) and capture the raw decoded string
   verbatim — including any prefix, suffix, control or padding characters.
3. Record the symbology reported by the scanner. Do not assume it from the label's
   appearance.
4. Derive the field structure; write it as a `barcode_profiles` row.
5. Validate the profile against the full sample set in a dedicated test fixture.
6. Confirm `CFG-01` (pallet uniqueness, `OI-02`) against the parsed sample — specifically,
   check whether any pallet number repeats across different jobs.
7. Activate via `CFG-02`.

Until step 7, `RAW_REFERENCE` remains active and Customer/LPO are populated by import
(`OI-11`) or left empty and clearly marked as "not encoded on label" in the UI — never
fabricated.

### 2.4 Validation on scan

| Check | Failure |
|---|---|
| Non-empty after trimming control characters | `PALLET_BARCODE_UNREADABLE` |
| Length within the profile's expected bounds | `PALLET_BARCODE_INVALID` |
| Profile parses successfully | `PALLET_BARCODE_INVALID` |
| Required fields present for `CFG-01` | `PALLET_IDENTITY_INCOMPLETE` |
| Not a **location** barcode (checked against `location_barcodes`) | warning: "That is a location barcode" |

The last check is worth its cost: an operator scanning a location label when the app wants a
pallet label is a routine mistake, and a specific message resolves it instantly.

### 2.5 Damaged pallet barcode (BRD §21 row G)

Manual search-and-select, restricted to `scan.manual_override` (Supervisor and above,
pending `OI-14`). Every use writes an `audit_log` row with event `override.used`, the
justification text, the pallet selected and the operation performed. Re-labelling a damaged
pallet is an ERP-side process and is explicitly outside this system.

## 3. Part B — Location barcode

### 3.1 Identity rules

| Rule | Statement |
|---|---|
| LB-01 | Every storage location has exactly one barcode identity — `UNIQUE(location_id)` on `location_barcodes` |
| LB-02 | Every barcode value is globally unique — `UNIQUE(barcode_value)` |
| LB-03 | **A reprint reproduces the same value.** It touches `last_printed_at` and `reprint_count` only. |
| LB-04 | The value changes only by an explicit, separately-permissioned master change, which writes an audit row carrying both old and new values |
| LB-05 | A location's barcode value is never reused by another location, even after the original is deleted |
| LB-06 | The printed label carries the human-readable Location ID beneath the barcode (BRD §18) |

LB-03 is the requirement most likely to be violated by a careless implementation — a
"regenerate" button next to "reprint" is all it takes. There is no regenerate endpoint.
`POST /location-barcodes/{id}/reprint` has no code path that writes `barcode_value`, and a
test asserts that the value is unchanged after a reprint.

### 3.2 Value format

Two supported sources (BRD §7: "System-generated code or customer-provided existing location
code must be supported"):

| Source | Behaviour |
|---|---|
| `SYSTEM_GENERATED` | Pattern from `CFG-21` `barcode.location_pattern`, default `LOC-{site}-{facility}-{zone}-{seq}` with tokens resolved from the master record. Uniqueness verified on write. |
| `CUSTOMER_PROVIDED` | The customer's existing location code is used verbatim as the barcode value. Validated for uniqueness and for symbology-safe characters. |

The customer's numbering convention is `OI-03`. The default pattern is a placeholder that
produces valid, unique codes; it is **not** presented as the customer's convention.

### 3.3 Symbology

| Item | Default | Setting |
|---|---|---|
| Symbology | `CODE128` | `CFG-03` |
| Alternatives | `CODE39`, `QR`, `DATAMATRIX` | |
| Rationale | Code 128 is dense, alphanumeric, and universally supported by industrial 1D/2D imagers. QR is offered for locations where the label may be scanned at an angle or partially obscured. | |

Final choice depends on the confirmed PDA (`OI-07`) and label printer (`OI-13`).

### 3.4 Label layout

```
┌────────────────────────────────────┐
│  [ optional site / facility name ] │
│                                    │
│  ███ ██ ████ █ ███ ██ █████ ██     │   ← barcode, ≥ 15 mm tall
│                                    │
│         A - 02 - 14                │   ← Location ID, large, human-readable (LB-06)
│    Yard A  ·  Zone 2               │   ← context line
└────────────────────────────────────┘
```

Default output is a **PDF label sheet** (configurable label size, N-up layout), which works
with any office or label printer and locks the customer into nothing. Direct ZPL/EPL output
is an add-on once `OI-13` confirms the printer.

### 3.5 Print, preview and reprint workflow

| Action | Endpoint | Permission | Audit |
|---|---|---|---|
| Preview one | `GET /location-barcodes/{id}/preview` | `barcode.print` | — |
| Print batch | `POST /location-barcodes/print` | `barcode.print` | `barcode.printed` with the location id list |
| Reprint one | `POST /location-barcodes/{id}/reprint` | `barcode.reprint` | `barcode.reprinted` with reason and reprint count |

The reprint confirmation dialog states, verbatim: *"This reprints the same barcode value.
The location identity will not change."* — because the operator's mental model of "reprint"
is often "make a new one".

### 3.6 Damaged location barcode (BRD §21 row F)

Two sanctioned paths, both audited:

1. **Reprint** the label (`barcode.reprint`) — the correct fix, since identity is preserved.
2. **Manual location selection** (`scan.manual_override`) — an interim measure so work
   continues, recorded on the transaction as a manual override with justification.

Neither path is available to `PDA_OPERATOR` by default (`OI-14`).

```
        ┌────────────────────┐                ┌────────────────────┐
        │  ERP pallet label  │                │  Location label    │
        │  (customer's ERP)  │                │  (this system)     │
        └─────────┬──────────┘                └─────────┬──────────┘
                  │ scan                                │ scan
                  ▼                                     ▼
        ┌────────────────────┐                ┌────────────────────┐
        │ debounce CFG-05    │                │ debounce CFG-05    │
        └─────────┬──────────┘                └─────────┬──────────┘
                  ▼                                     ▼
        ┌────────────────────┐                ┌────────────────────┐
        │ BarcodeProfile     │                │ lookup             │
        │ Parser (CFG-02)    │                │ location_barcodes  │
        └─────────┬──────────┘                │ UNIQUE(value)      │
                  ▼                           └─────────┬──────────┘
        ┌────────────────────┐                          ▼
        │ ParsedPallet       │                ┌────────────────────┐
        │ Identity           │                │ LocationValidator  │

                    │  lock · validate · commit│
                    └──────────────────────────┘
```

## 6. Test coverage required

- [ ] `RAW_REFERENCE` profile stores and resolves an arbitrary scanned string
- [ ] Each parsing strategy against a fixture of representative values
- [ ] Malformed, empty, truncated and control-character-laden input rejected cleanly
- [ ] A location barcode scanned where a pallet is expected produces the specific warning
- [ ] **Reprint leaves `barcode_value` byte-identical** and increments `reprint_count`
- [ ] Barcode value uniqueness enforced at the database level (attempt a duplicate insert)
- [ ] Deleting a location does not free its barcode value for reuse (LB-05)
- [ ] Manual override without permission returns 403 and writes no transaction
- [ ] Manual override with permission writes an `override.used` audit row carrying the justification
- [ ] Generated label PDF contains the human-readable Location ID (LB-06)
