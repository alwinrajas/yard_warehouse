**Domain:** Aluminium Channels / Profiles Manufacturing

## 1. Purpose of this document

This document establishes the agreed reading of the BRD before any code is written. It
separates what is **confirmed**, what is **configurable**, what is **still an open customer
input**, and what we are **deliberately refusing to assume**.

No requirement in this document has been invented. Every statement is traceable to a BRD
clause, or is explicitly marked as an open item (`OI-nn`), configuration point (`CFG-nn`) or
recorded assumption (`ASM-nn`).

---

## 2. Scope boundary (non-negotiable)

Derived from BRD §4.1, §4.2, §4.3, §25.

### 2.1 Where the system starts
A completed production pallet carrying the **existing ERP-generated barcode label** is
present at the production collection / pickup point.

### 2.2 Where the system ends
The pallet is picked from its recorded storage location, moved to the dispatch/loading
area or vehicle, verified by scan, and marked **Dispatched**. History and reporting
continue indefinitely after that point.

### 2.3 Tracked lifecycle

```
Production Collection Point
   -> Put-Away
      -> Stored Location
         -> Internal Movement (0..n)
            -> Pick / Dispatch
               -> History & Reporting
```

### 2.4 Explicitly NOT built (BRD §25)

| # | Excluded | Note |
|---|----------|------|
| X-01 | Production planning / execution | Remains in ERP |
| X-02 | Customer order creation | Remains in ERP |
| X-03 | Replacement of ERP pallet barcode generation | **We scan it, we never issue it** |
| X-04 | ERP API / database integration | Separate commercial phase |
| X-05 | Vehicle routing / transport management | Out |
| X-06 | Proof of delivery beyond `Dispatched` status | Out |
| X-07 | RFID, GPS forklift tracking, PLC/crane, computer vision | Out |
| X-08 | Offline synchronisation on the PDA | Only after connectivity assessment (`OI-08`) and agreed conflict rules |

`X-08` is a design constraint, not just a scope note: the PDA is built **online-first**. No
local transaction queue is implemented. Every state-changing action blocks on a confirmed
cloud commit (BRD §21, network-interruption row).

## 3. The two barcode concepts

This is the single most misread part of the BRD, so it is stated separately.

| | **A. ERP Pallet/Job Barcode** | **B. Storage Location Barcode** |
|---|---|---|
| Generated by | Customer's existing ERP | **This application** |
| Our responsibility | Scan, decode, validate, store the reference | Generate, preview, print, reprint |
| Identity ownership | ERP owns it | We own it |
| Re-issue | Never by us | Reprint reproduces the **same** value (BRD §18) |
| Data carried | Job No., Pallet No., Customer, LPO — *extent unconfirmed* (`OI-01`) | Unique location code + human-readable Location ID |

**Rule:** reprinting a location label must never mint a new location identity. The barcode
value changes only when an authorised administrator deliberately changes the Location
Master, and that change is audited.

Super Admin, Warehouse/Yard Admin, Warehouse In-charge/Supervisor, Forklift/PDA Operator,
Management/Viewer. Individual credentials per user. **Shared operator credentials are
prohibited** — this is enforced, not advisory (see `docs/07-permission-matrix.md`).

| Area | Requirement | Design response |
|---|---|---|
| Availability | Cloud-hosted, secure internet access | AWS, HTTPS-only, ALB health checks |
| Performance | Scan validation/posting "within a few seconds" | Budget: p95 ≤ 800 ms server-side for scan endpoints |
| Concurrency | Simultaneous PDA + web users, no duplicate updates | Pessimistic row locking + unique constraints + idempotency |

| Device | Android industrial PDA, 1D/2D scanner; model TBC | Scanner abstraction layer (`OI-07`) |

## 5. Requirements requiring interpretation

Where the BRD is ambiguous, the rule applied is: **use the BRD wording as baseline, choose
the least-assumptive implementation, and make it configurable.** Each decision below is
recorded with its rationale.

### AMB-01 — Pallet uniqueness
- **BRD text:** §26 asks the customer to confirm whether `Job Number + Pallet Number` or
  `Pallet Number` alone is globally unique.
- **Impact:** This determines the identity key of the entire inventory. Choosing wrongly in
  the direction of `Pallet Number` alone would **merge two physically distinct pallets into
  one record** and corrupt inventory irrecoverably. Choosing `Job + Pallet` when only
  `Pallet` was needed is harmless — it produces a strictly finer-grained key.
- **Decision:** Default `CFG-01 = JOB_PALLET`. Identity is a stored canonical column
  `pallet_key`, derived by the configured rule and protected by a UNIQUE index.
- **Guard:** The setting becomes **immutable once any inventory transaction exists**. Changing
  it afterwards requires a documented, scripted data migration — not a settings toggle.

### AMB-02 — Pallet status vs. hold/exception state
- **BRD text:** §8 lists `At Collection Point, Stored, In Movement, Staged for Dispatch,
  Dispatched, On Hold, Damaged/Exception` as one status list. §13 separately requires that a
  held pallet remains blocked "until released by an authorized user".
- **Impact:** If `On Hold` overwrites `Stored`, the system loses *where the pallet is* while
  it is held, and release has no state to return to. Reports for "location-wise stock" would
  silently drop held pallets.
- **Decision:** Two orthogonal fields — `lifecycle_status` (where it is) and `block_state`
  (whether it may move/dispatch). A derived `display_status` reproduces the BRD's single
  list for all UI and reports, so the customer-visible vocabulary is unchanged.
- **Documented as:** `ASM-01`.

### AMB-03 — Transfer as one step or two
- **BRD text:** §9.2 describes scan pallet → verify source → physically move → scan
  destination → confirm.
- **Impact:** If the PDA posts a "picked" transaction before the physical move, an
  interrupted move leaves the pallet in `In Movement` with no location — an orphan the BRD
  §21 explicitly calls out as an exception to be resolved by supervisor correction.
- **Decision:** Default `CFG-08 = SINGLE_STEP`: source and destination travel in **one atomic
  API call**, so an abandoned move simply leaves the pallet at its original location. A
  `TWO_STEP` mode (which uses the `In Movement` status) is implemented but off by default.

### AMB-04 — Direct dispatch vs staging
- **BRD text:** §9.3 "Optionally, a staging step can be used before final dispatch
  confirmation." §26 asks the customer to confirm.
- **Decision:** Both implemented. Default `CFG-09 = DIRECT` (fewest states, matches the
  numbered flow in §9.3). `STAGED` enables the `Staged for Dispatch` status.

### AMB-05 — Extent of data in the ERP barcode
- **BRD text:** §4.3 — "If the existing barcode encodes all required values … If it encodes
  only a reference number …"
- **Impact:** Determines whether Customer and LPO are captured at scan time or must be
  imported.
- **Decision:** A pluggable barcode-profile parser. Default profile is `RAW_REFERENCE` —
  we store exactly what was scanned and enrich from imported pallet master data. No parsing
  rule is invented before real label samples arrive (`OI-01`).

### AMB-06 — Location capacity
- **BRD text:** §7 "capacity (optional)", §11.3 "Optional capacity control if the customer
  defines how many pallets each location can hold."
- **Decision:** `locations.capacity` is nullable. `CFG-06 = OFF` by default; `WARN` and
  `BLOCK` modes implemented and inert until the customer defines capacity (`OI-04`).

### AMB-07 — "Real-time" web updates
- **BRD text:** §11.4 "Real-time list of …"; master prompt §32 forbids introducing Redis
  solely for real-time.
- **Decision:** Server-driven polling with `ETag`/`Last-Modified` on dashboard and inventory
  endpoints (default 15 s, configurable). This satisfies "web reflects new state immediately
  after commit" with zero additional infrastructure. WebSocket push (Laravel Reverb, no
  Redis on a single node) is documented as an approved upgrade path, not a phase-1 build.

## 7. Recorded assumptions

Assumptions are minimised deliberately. Those that remain are listed so they can be
challenged at review.

| ID | Assumption | Why it is safe | Reversal cost |
|---|---|---|---|
| ASM-01 | Lifecycle status and block state are separate fields, presented to users as the single BRD status list | Preserves location during hold; no vocabulary change for users | Low — presentation-layer mapping |
| ASM-02 | One user has exactly one role (BRD §6 and User Master both use singular "Role") | Matches BRD wording | Low — join table already models it as many-to-many-capable |
| ASM-03 | A pallet record is created on first scan if it does not already exist, with whatever data the barcode yields | BRD §4.3 permits standalone operation from the label alone | Low |
| ASM-04 | Dispatch is terminal; un-dispatch is possible only via the audited correction workflow | BRD §12 dispatch-validation rule | Low |
| ASM-05 | Sizing baseline for phase 1: ≤ 50,000 active pallets, ≤ 20,000 locations, ≤ 50 users, ≤ 5,000 movements/day | Order-of-magnitude placeholder pending `OI-06`; drives index choice only | Medium — re-run load test |
| ASM-06 | "Device/session" in the audit trail means PDA device identifier + auth token identifier | BRD §15 says "device/user session" without defining it | Low |
| ASM-07 | Exports are generated server-side and delivered as downloadable files (Excel + PDF) | BRD §11.2 "Export … to Excel/PDF" | Low |

## 8. Deliberate non-assumptions

The following were **not** invented, despite being tempting:

- No ERP endpoint, table, or credential is referenced anywhere in the codebase.
- No barcode field layout, delimiter, or fixed-width map is coded until `OI-01` is answered.
- No customer name, site name, facility name, zone name, or location code is seeded as
  production data. Seeders contain only obviously-marked demo data used by tests.
- No capacity numbers, ageing thresholds, or password-policy values are hard-coded.
- No offline queue, conflict-resolution rule, or sync protocol is designed.
- No SLA/uptime figure is claimed; the BRD states none.
- Backup/recovery is not described as "complete" until it is actually provisioned and a
  restore has been rehearsed (master prompt §34).
